# Frontend requirements and review

This frontend stage implements the approved site changes in `docs/V3.md` items 23–26 and `docs/site-rows.md`. Contract source and deployment remain unchanged. The site retains the existing dark, green, monospace visual system and all eight routes. The only current deployment map is loaded from the exported `imd-deployment.json`; application ABIs are fetched from that file’s references.

## Better Interface coverage and fixes

The pinned guide’s workflow and core principles for accessibility, layout, writing, typography, colors and UI informed these changes. Existing design tokens and visual identity were retained.

| Domain | Applicable finding and correction |
| --- | --- |
| Accessibility | Oracle acknowledgement was distant from its first action, and disabled reasons did not focus it. It now has one state and an explicit focus link (`web/src/Claim.tsx:156`). Transaction buttons have adjacent status announcements. Step headings and payment radio grouping are semantic. |
| Layout | Wide desktop tables and a separate step-number column compressed mobile content. Tables now wrap into readable rows and step bodies span the content area (`web/src/components.tsx:24`, `web/src/styles.css`). The hourly table remains the documented exception. |
| Writing | A historical 0.5 IMD claim figure and fixed combined registration cost could be wrong. They now describe or read the live price, explain that it changes and distinguish registration from the first claim (`web/src/Claim.tsx:115`). Removed transaction paths no longer appear in current copy. |
| Typography | Instructions were placed in the citation class. Narrative helper paragraphs now use muted body text; citations retain the smaller citation role (`web/src/pages.tsx`, `web/src/components.tsx`). Type sizes are source-defined tokens in the existing mono system. |
| Colors | Journal failures and success used the same neutral state treatment. Failed/rejected/unknown and confirmed now use the existing danger and accent roles. No palette change was introduced (`web/src/styles.css`). |
| UI | The mint image was a generic example after connection. It now follows the connected account, reads its token state and disables an already-completed mint (`web/src/Claim.tsx:63`). Origin and prepared links connect the action to its transaction journal. |

Rendered coverage, measured contrast, the design probe and baseline browser results are recorded with the final validation evidence. Do not interpret the source review as an attestation that those tools ran.

## Focused interaction validation

`web/tests/site-browser.mjs` exercises the production export through deterministic EIP-6963 and Ethereum JSON-RPC fixtures. It is deliberately read-only: a signing/broadcast method is an assertion failure. Fixtures are isolated to the test process; they are not application fallbacks or deployment configuration.

The focused checks cover non-Curator request guards, the single acknowledgement and focus link, exact fact/price/origin review, an insufficient-IMD error under the affected journal step, local spec-field errors, registration’s click-time price refresh, connected minted/unminted card behavior, Explorer request links, stored Swarmed windows, 390 px table widths, trait deep links, recovery from an RPC outage, and integration copying. The final production-export run of `node web/tests/site-browser.mjs` passed **14 of 14 checks** in Chromium. There were no page errors, unhandled fixture RPC methods or transaction broadcasts. Explorer’s three responsive table wrappers measured 358 px wide with 358 px scroll width at a 390 px viewport. Catalog, comparison and claim table wrappers also fit without sideways scrolling. The acknowledgement and first gated button occupied a 189.6 px vertical span. The result binds to final deployment-manifest SHA-256 `c36c1365e1476e999fa64d46e58639aedce4d83de04b12524f84faa250fd155b`. Actual results are in `docs/evidence/site-browser-results.json`; table-body screenshots are in `docs/evidence/site-tables/`. The insufficient-balance and connected-card screenshots are stored alongside that result.

No funded wallet transaction is required by this frontend stage. Real extension/native-wallet confirmations and a live economic swap remain unperformed; deterministic provider and transaction-flow tests exercise these paths without spending funds. External attestation links are user-initiated navigation; the application does not fetch the attestation API.
